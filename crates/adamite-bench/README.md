# adamite-bench

Unpublished development binary measuring the production `ImageReader` → `SyncDriver` → `Scanner` path, followed by `ScanOutput::to_bytes` and `ScanOutput::from_bytes`.

```sh
deno task bench
deno task bench --in-use 300000
deno task bench --in-use 300000,1000000 --output-dir target/bench
deno task bench --in-use 300000 --trace-chrome target/bench/trace.json
```

The default cases contain 300,000 and 1,000,000 in-use records. Images are generated by `adamite-fixtures::SyntheticVolume` into `target/bench`. Versioned filenames encode every workload setting; complete images of the expected length are reused. Generation writes to a temporary file and publishes it after flushing and syncing. Each case runs in a fresh child process of this binary, after image generation, so heap peaks do not include generation or earlier cases. With multiple counts, `--trace-chrome trace.json` writes `trace-300000.json` and `trace-1000000.json`.

The reference mix uses 1 KiB records, 4 KiB clusters, contiguous non-resident MFT DATA and MFT BITMAP, and zero-filled free slots at 25% of ordinary in-use records plus reserved system slots. The resulting slot counts are 375,032 and 1,250,032. Every in-use record has standard information. Ordinary names have 20 UTF-16 units, about 5% of ordinary records are directories, and about 23% have DOS aliases. Files hold either 64 resident DATA bytes or one four-cluster non-resident segment; payload regions remain sparse holes. The scanner reads no payloads or bitmap bytes.

The first Markdown table reports slots, in-use records, MFT bytes, source bytes read, elapsed milliseconds, overall peak requested heap and final snapshot heap. Bytes read are counted once by a `VolumeReader` wrapper. Elapsed time covers scanning, encoding and decoding, including release of the original output before decoding. Final snapshot heap is the live requested heap immediately after the scan returns, including executable and profiling overhead. Overall peak covers the complete measured case.

The second table reports each production stage's creation-to-close duration, its own maximum live requested heap and signed heap delta. `adamite-profile::SpanRecorder` supplies these summaries from the same `HeapLayer` used by Chrome tracing. Peaks are absolute live byte counts during each stage, including nested spans and profiling overhead. They are not resident memory measurements. Chrome trace output adds writer and event storage overhead, so collect baseline tables without tracing. Open traces in Perfetto or `chrome://tracing`.

`deno task check` builds, tests and lints this workspace member, including Windows cross Clippy, without running the large benchmark. Unit tests use tiny images and check cache reuse, byte counts, scan diagnostics and exact persistence round trips. Heap regression budgets will be added in M3 after ingest and stage overlap changes establish the budgets.
